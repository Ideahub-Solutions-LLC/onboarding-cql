1. DOWNLOAD AND OPEN
Download CQL-Onboarding-Source-v3.zip from the shared Drive folder. Extract cql-onboarding and open that directory in your editor. Use Node.js 24 or newer (tested here with 26.7) and npm. Keep package-lock.json.

  npm ci
  npx tsc --noEmit

  node tests/pricing.mjs

Initialize a fresh local database after the first build, once:

  npx wrangler d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_steady_shard.sql

Then start the browser preview:

  npm run dev

Open http://127.0.0.1:5173 and use the local preview sign-in. The preview uses synthetic local identity. Never expose this development server to real clients. The local data remains in .wrangler/state and is not included in the source package. If an existing local database already has the tables, do not re-run the initial CREATE TABLE script.

For a local vault preview, configure a new 32-byte base64 VAULT_KEY in the local ignored .dev.vars location supported by your Wrangler/Vite setup. Use your secret manager to generate and store it. Production uses a different secret. Do not use the synthetic test value in production.

4. AUTHENTICATION - REQUIRED FOR YOUR OWN URL
app/chatgpt-auth.ts currently trusts identity headers supplied by the Sites hosting layer. Those headers are NOT sufficient authentication on a directly exposed Worker. Do not publish this build unchanged at a workers.dev or custom domain.

Replace getChatGPTUser with your verified authentication provider or a properly validated Cloudflare Access identity. Validate signature, issuer, audience, expiry, and intended application; use a stable verified subject for userId and a verified email. Never trust a caller-supplied oai-authenticated-user-* header. Strip/ignore such headers at any public entry point. Replace the /signin-with-chatgpt UI link with the chosen login flow. Test sign-out and session expiry.

The current first-authenticated-visitor ownership bootstrap is intended for an owner-private Sites deployment. For independent hosting, pre-provision the approved owner using the provider's stable user ID, or require an explicit owner allowlist before initialization. Do not let the first public visitor become administrator. Preserve per-application authorization and same-origin write checks. 6. DATABASE AND FILES
D1 tables: settings, applications, attachments, secrets. The initial SQL is drizzle/0000_steady_shard.sql. settings contains owner and config. Application data includes step answers, completion markers, requestedFeatures, status, notes, checklist, and a submitted pricing snapshot. R2 objects are private uploads; attachments provides metadata and application ownership. secrets holds AES-GCM encrypted values, with application ID used as authenticated additional data.

Uploads: up to 10 MB each, up to 30 per application. Accepted types: PDF, PNG/JPG/WebP, CSV/TSV, Excel, Word, and text. Uploaded price documents accept PDF, Excel, CSV. Prices are configuration data; a CSV import changes rate rows after preview and Save settings. A PDF/Excel document upload is a separate customer download and does not extract rates automatically.

Back up D1, private R2, and the vault key as separate protected resources. Test restoring all three together. Define document retention and credential deletion procedures before real client use. Add an audit log, operational monitoring, rate limits, and file inspection appropriate to your deployment before accepting sensitive ID documents at scale. The included validation does not scan upload content for malware.
